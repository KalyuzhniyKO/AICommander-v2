# Подготовка #22: проверяемые SQLite backup/restore

[English](SQLITE_BACKUPS.en.md) · [Issue #22](https://github.com/KalyuzhniyKO/AICommander-v3/issues/22)

`python -m backend.app.storage.backup` — явный offline-инструмент для состояния
AICommander и отдельного budget ledger. Использует только stdlib. Не читает `.env`,
не ищет БД автоматически, не запускает приложение, миграции, модели или recovery.
Постоянные БД и сервисы в ходе этой подготовки не использовались.

## Команды на собственном тестовом файле

Укажите существующий workspace и SQLite-файл явно. Здесь `fixture.sqlite3` —
**ваша отдельная тестовая БД**, не база склада и не автоматически выбранная БД приложения.
Родительский каталог выходного файла должен существовать.

```bash
mkdir -p .aicommander-backups
python -m backend.app.storage.backup create --root . --source fixture.sqlite3 --output .aicommander-backups/state.aic-backup.zip
python -m backend.app.storage.backup verify --root . --source .aicommander-backups/state.aic-backup.zip
python -m backend.app.storage.backup restore --root . --source .aicommander-backups/state.aic-backup.zip --output restored-new.sqlite3
```

Успех — exit 0 и JSON с `verified=true`. Ошибка — exit 2 и стабильный `code`, без
содержимого БД, путей, SQL или исходного текста исключения. `--help` показывает
аргументы. По умолчанию: `--timeout-seconds 30`, `--max-bytes 268435456` (256 MiB
для SQLite). Допустимые пределы: 1–120 секунд и 1 byte–1 GiB. Лимит времени
проверяется в backup progress, SQL progress и при потоковом чтении/хешировании;
это не OS watchdog и не гарантия прерывания зависшего системного I/O.

## Формат и проверки

Формат v1 — ZIP_STORED строго с двумя файлами: `state.sqlite3` и `manifest.json`.
Нет extractall, сжатия, ZIP64, комментариев, произвольных имён или вложенных путей.
Размер/count центрального каталога проверяется **до** создания ZipFile объектов;
затем проверяются методы, типы members, CRC, размеры и JSON без duplicate keys.
Manifest содержит SHA-256/размер SQLite, UTC-время, версию SQLite runtime и
метаданные: версии схем, количества строк и неразрешённых состояний. Пути,
описания задач, ответы моделей и credentials не выводятся в manifest.

Создание использует **SQLite Connection.backup**, не копирование основного файла
через filesystem. Включаются подтверждённые изменения из WAL. На копии journal
переводится в DELETE, чтобы она не зависела от внешних WAL/SHM. Выполняются
integrity_check, foreign_key_check и проверка поддерживаемой схемы. Артефакт
повторно читается/проверяется перед публикацией.

Проверка и restore заново сверяют размер/SHA-256 и производные metadata, затем
integrity/FK/schema. Поддерживаются legacy app, taskflow migrations 1/2/3,
panel migration 1 и budget schema 1; пустые/частичные/будущие несовместимые схемы
отклоняются. Данные не мигрируются. Если app и budget находятся в разных файлах, для
согласованного набора остановите всех writers перед копированием обоих:
отдельные снимки не образуют общую транзакцию. Используйте инструмент версии, совместимой
со схемой приложения, а не обходите отказ старого инструмента.

**SHA/CRC — проверка целостности, не подпись и не доказательство авторства.**
Доверяйте только собственным резервным копиям. Согласованный снимок отражает одну
точку времени, не все будущие записи параллельного writer.

## Файлы и границы

Источник и назначение должны находиться внутри явного workspace. `..`, выход
за root, symlink-компоненты (включая source WAL/SHM/journal), hardlink-источники и root равный home/filesystem root
отклоняются. Эти проверки не являются песочницей против злоумышленника с правами
владельца workspace; защищайте сам каталог и права доступа.

Промежуточные файлы создаются в приватном каталоге на том же filesystem, данные
синхронизируются fsync. Публикация через exclusive hardlink не заменяет существующий
файл даже при гонке. Если filesystem не поддерживает hardlink, операция завершается
ошибкой, без небезопасного fallback. На POSIX права выходных файлов 0600; на Windows
нужны также подходящие ACL каталога. Отдельная гарантия power-loss/directory durability
для всех платформ не заявляется. После ошибки проверяйте наличие/валидность результата
перед повтором: редкий сбой cleanup после публикации может оставить полную копию.

Restore создаёт **только новый** файл. Существующее назначение, даже пустое, и
остаточные `-wal`/`-shm`/`-journal` у этого имени блокируют восстановление.
Нельзя использовать restore как способ перезаписать работающую БД. Выбор БД
приложения и переключение конфигурации выполняются отдельно владельцем после
приёмки; инструмент не меняет `DATABASE_URL`.

Архив содержит полный SQLite без редактирования пользовательского содержимого:
это **приватные данные**, потенциально включая чувствительные тексты/старые логи.
ZIP не зашифрован. `.env`, SSH-ключи, Git-файлы, конфигурации Hermes/OmniRoute и
моделей не включаются как отдельные файлы. Храните копии в защищённом месте.
`.gitignore` исключает обычные snapshot/SQLite/sidecar имена и каталог
`.aicommander-backups`; это не заменяет проверку состава Git-коммита.

## Состояние после restore

Сохраняются строки, ID, версии, артефакты v1/v2, provenance, commands/idempotency,
operation journal и бюджетные резервы. `running/result_ready/unknown`, а также
budget `reserved/dispatched/unknown` **не** переводятся автоматически в success,
не удаляются и не освобождаются. Повторные разрешения не выдаются.

`operator_recovery_required` показывает наличие сохранённых неразрешённых
состояний; это не сканирование процессов и не доказательство их остановки.
**Перед использованием восстановленной БД остановите приложение и всех workers,
включая использующих исходную БД.** Старый и восстановленный файлы — независимые
копии; запуск обеих может дублировать внешние эффекты. Затем проверьте
[протокол операций](OPERATIONS.md) и [budget limitations](BUDGETS.md). Снимок может предшествовать уже выполненному внешнему вызову и откатывать
историю idempotency/claim. Даже остановка workers не доказывает, что reserved
или отсутствующую в снимке операцию можно отправить снова. Restore всегда
возвращает `external_effects_reconciliation_required=true`: перед возобновлением
нужна сверка с последним доверенным внешним журналом/биллингом, в том числе
когда `operator_recovery_required=false` по данным самого снимка. Snapshot
хранит данные, но не подтверждает фактический исход inference/billing. Инструмент
не запускает это восстановление сам и не обещает exactly-once оплату.

## Доказательства и остаток #22

[QA](qa-issue-22-backup.json) · [Пример manifest на синтетической БД](contracts/sqlite-backup-v1.example.json).
Тесты используют настоящие временные SQLite, WAL без checkpoint, конкурентного
writer и subprocess CLI. Проверяются v1/v2 артефакты, неизвестные операции,
бюджетный unknown fence, checksum/metadata/format ошибки, FK/schema, лимиты,
отказ от symlink/hardlink/escape и перезаписи, гонка публикации и cleanup.

Полная #22 остаётся открытой: установка/обновление/rollback в чистой тестовой
Zorin-среде, защищённый доступ MacBook, эксплуатационные health/metrics и приёмка
владельца требуют следующих интеграционных проверок. Никакого deploy, нового
systemd/Compose сервиса, расписания backup или обращения к Zorin здесь нет.
