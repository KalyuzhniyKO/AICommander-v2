# Product specification: AICommander 3.0

## Objective
Build a virtual AI software team to maintain `warehouse_config` and create other software, directed from a MacBook by a human owner. Use already configured Zorin OS Hermes and OmniRouter, not a second routing system.

## Roles and outcomes
| Role | Responsibility | Verifiable artifact |
|---|---|---|
| Owner (human) | task, business decision, budgets, approval | task / approval |
| Director (Hermes) | triage, choose minimal team, delegate, control progress | task plan and decision trail |
| Analyst | requirements, user flows, acceptance criteria | requirements.md |
| Architect | architecture, migrations, security/rollback plan | design.md |
| Developer | changes in isolated worktree; Codex CLI for complex changes | commits / git diff |
| QA | run actual tests, collect exit codes / stdout, regression | qa-report.json |
| Reviewer | independent risk/diff review and testing audit | review.md |
| Owner (human) | explicit approval before merge and deploy | approval decision |

## Task difficulty and model selection
- Simple: available free/low-cost model via OmniRouter for analysis/review; real tests always.
- Medium: role-appropriate model based on capabilities, availability, quota and cost.
- High-risk/complex: supported Codex CLI integration for code execution; manual ChatGPT browser handoff for expert discussion, not a scraped API.
- Failed/429/quota: model fallback and bounded retry, never present fallback messages as successful code changes.

## Workflow
`NEW -> TRIAGE -> REQUIREMENTS -> (PLAN) -> IMPLEMENTATION -> QA -> REVIEW -> WAITING_OWNER -> DONE` with explicit FAILED/BLOCKED/RETRY/REJECTED states.
- AI Director can skip roles only when justified; QA of changed code is not skippable.
- Every role receives prior artifacts (not merely the original user prompt).
- User may stop/resume, reject, request adjustments or approve the plan.
- Budget, time and attempts are capped by task.
- Test evidence is generated by real commands executed against an isolated copy.
- GitHub PR is created only from a separate branch after QA, with owner-controlled merge.

## Runtime and safety
MacBook: web dashboard, GitHub notifications and approvals.
Zorin: running Hermes/OmniRouter + isolated execution of workers/staging.
Lenovo Omarchy: optional extra development worker, not required.
Use authenticated service over VPN/SSH only after security is implemented. No internet-exposed unauthenticated UI. Don't grant agents production secrets or direct write access to deployment endpoints.

## Acceptance for first working product
From MacBook, submit one harmless change to a test checkout of `warehouse_config`; Director assigns analyst/coder/QA/reviewer; actual files change in isolated branch; pytest/Django checks run and produce logs; draft PR is shown; owner approves/rejects; no unintended changes to production.
